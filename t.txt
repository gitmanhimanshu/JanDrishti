# JAN DRISHTI

## See. Suggest. Solve.

You are a **Principal Software Architect, OOSD Expert, Senior Django/DRF Engineer, Senior Next.js/TypeScript Engineer, PostgreSQL Database Architect, Security Engineer, DevOps Engineer, Product Designer and UX Architect**.

Your task is to design and build a **production-grade, scalable, secure and maintainable full-stack civic technology platform called JanDrishti**.

Do not treat this as a tutorial project or a simple CRUD application.

Build it as a serious product that can evolve from thousands of users to **10M+ users**.

---

# 1. PRODUCT NAME

## JanDrishti

### Tagline

**See. Suggest. Solve.**

Meaning:

* **Jan** = People/Public
* **Drishti** = Perspective/Vision

The product should represent the collective perspective, experience and intelligence of citizens and professionals.

Core philosophy:

> **See → Report → Support → Suggest → Act → Prove → Impact**

# 2. PRODUCT VISION

JanDrishti is a **public-first civic intelligence and action platform**.

It brings together:

1. Public Problems
2. Evidence
3. Community Support
4. Professional Experience
5. Expert Recommendations
6. Government Action
7. Transparent Progress
8. Proof of Work
9. Future Community Projects/Funding

The platform should help answer:

> What is the problem?

> Where is it happening?

> How many people are affected?

> What evidence exists?

> What do experienced people recommend?

> Which department is responsible?

> What action has been taken?

> What has actually been completed?

> Where is the proof?

The central product lifecycle is:

**Problem → Evidence → Experience → Recommendation → Action → Proof → Impact**

Do NOT make JanDrishti look like a traditional government complaint portal.

It should look like a modern, trustworthy civic-tech platform.

# 5. LOGIN REQUIRED ONLY FOR INTERACTION

If an anonymous user attempts an action that changes data or represents participation, require login.

Examples:

* Support a Problem
* "I face this problem"
* Support an Experience
* Comment
* Reply
* Bookmark
* Follow
* Report content
* Submit a Problem
* Submit Experience
* Upload evidence
* Create a Project
* Contribute to a project
* Submit professional verification
* Update profile
* Any other write operation

Use a reusable frontend mechanism:

```text
requireAuth(action)
```

Flow:

```text
Anonymous User
      ↓
Clicks "Support this issue"
      ↓
Authentication check
      ↓
Not authenticated
      ↓
Login Modal
      ↓
Continue with Google
      ↓
Google OAuth
      ↓
JanDrishti account
      ↓
Return to original page
      ↓
Complete original action
```

Do NOT force the user to manually navigate back after login whenever it can be avoided.

# 19. ISSUE CLUSTERING

If 500 citizens report the same pothole/road problem:

Do not leave 500 unrelated issues for government operations.

Create an:

```text
IssueCluster
```

and connect individual reports to the cluster.

Architecture:

```text
500 Citizen Reports
       ↓
Duplicate Detection
       ↓
Issue Cluster
       ↓
Government Action
```

But preserve all individual reports.

Do not delete the original reports.

Show:

```text
Reported by 500 people
```

or similar meaningful aggregation.

Duplicate detection can use:

* geographic proximity
* category
* title similarity
* semantic similarity
* time
* visual similarity where appropriate

AI suggestions must remain reviewable.

# 29. VERIFICATION DOCUMENTS

Accept appropriate documents where relevant:

* Organization-issued document
* Employment/service document
* Retirement/service document
* Professional license/certificate
* Government-issued professional document
* Other legitimate supporting document

### Aadhaar fallback

If the user has no suitable professional document, allow an **optional Aadhaar-based fallback verification path**, subject to applicable law, privacy requirements and the actual verification provider used.

Important:

Aadhaar must NOT:

* be mandatory for all users
* be the primary database identity
* be used as login credential
* be displayed publicly
* be exposed through APIs
* be unnecessarily stored
* appear in URLs
* be shown in public profiles

Prefer a compliant verification mechanism that minimizes retention of Aadhaar data.

If document storage is technically required:

* store privately
* restrict access
* encrypt/protect sensitive data
* maintain audit logs
* apply retention/deletion policy
* never expose documents through public endpoints

* Load entire tables
* Return unbounded API lists
* Perform N+1 queries
* Perform unnecessary queries inside loops

---

# 49. CONCURRENCY

Handle concurrent requests correctly.

Example:

1000 users support the same Problem simultaneously.

Do NOT:

```text
read count
count += 1
save
```

Use:

* unique constraints
* transactions
* atomic database operations
* safe aggregation
* appropriate locking only where necessary

Use Redis distributed locks only where a genuine distributed locking requirement exists.

Do not use locks everywhere.

---

# 50. REDIS

Use Redis for appropriate workloads:

* caching
* rate limiting
* temporary state
* distributed coordination where necessary
* Celery broker/backend if selected

Do not treat Redis as the primary source of truth for transactional data.

---

# 51. CELERY / BACKGROUND JOBS

Use asynchronous processing for expensive operations:

* AI processing
* duplicate detection
* issue clustering
* media processing
* notifications
* emails
* analytics
* exports

Jobs must be:

* idempotent
* retry-safe
* observable
* failure-tolerant

Do not make users wait for expensive operations unnecessarily.
